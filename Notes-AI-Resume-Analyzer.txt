9.) Ever since we imported puter script inside root.tsx in app folder, the puter API became
    available in the entire application. 
    In puter.ts fil in app/lib, we have decalred a global interface window that defines all
    the functionalities that we can extract from window. So TS will now identify all these 
    functionalities throughout our project. This process is called decalration merging.
    A type is a label you give to a kind of value.
    In declaration merging, if there is an existing type, then any interface we declare with
    the same name will be merged in the existing type. In our case, the Window 
    interface is merged with the Window type. declare global tells TypeScript:
    “Hey TS, I want to add/extend types in the global scope, not just in this file.”
    Without declare global, your interface would be file-local, and window.puter would
    not be recognized in other files.
    Declaration Merging is a TypeScript feature that lets you combine multiple declarations
    of the same thing into one. Merging happens at compile time. Does not add anything at 
    runtime.
    The Puter store is almost identical to the window we have defined above. It is used by
    zustand to create a store, a place accessible from anywhere in our application, where we
    can store our data which in this case is Puter data.

12.) The below points are important to understand how the global Window interface and JS
     are in sync:
     a.) Window is the TypeScript interface describing the shape of the JS window object.
         window (lowercase) is the actual global object in JavaScript at runtime.
         In TypeScript, when you access window.someProp, TS checks it against the Window 
         interface. So in that sense, TS treats them as “connected,” but technically they 
         are different: one is type, one is object. By default, in TS the below line is 
         present, which makes Window take all properties of window:
         // TS knows the runtime `window` is of type `Window`
         const w: Window = window;
     b.) This Window interface is just for maintaining type safety at compile time. It is in
     this interface that declaration merging happens.
     c.) The runtime object window.puter must be created/assigned by actual 
     JavaScript code, otherwise you would get undefined and runtime errors.

16.) Why we call init() in useEffect in root.tsx:
     init() does async setup:
     a.) Waits for window.puter to load (polling)
     b.) Sets puterReady = true
     c.) Checks user auth status
     A side effect is any operation that touches the outside world (APIs, global objects,
     timers, navigation, async work). React requires such logic to run inside useEffect so
     renders stay pure and predictable.
     React requires side-effects in useEffect, not in the component body.
     If not done in root, child components might use Puter before it’s ready leading to
     errors.

17.) Why [init] is in the dependency array of useEffect in root.tsx:
     React’s rules of hooks: include all external vars/functions used inside useEffect. Since
     init changes things outside React’s render cycle like accessing window.puter, starts
     polling (setInterval), updates zustand store using set, and calls async auth checks, 
     hence it is a side effect and insidedependency array in useEffect.
     init reference is stable in Zustand, meaning the function object itself is created once
     React/Zustand does not recreate it on every render. This has nothing to do with
     isLoading, async/await, calling set etc. Those affect behavior, not identity.
     Zustand state updates do not re-run the store initializer
     They only mutate internal state. Functions inside the store are not redefined. So 
     Zustand returns same function refernce forever making init refernce stable.

18.) Why init() is in root.tsx and not elsewhere:
     root.tsx is the entry point → initialization happens once globally.
     Ensures all components relying on Puter store see consistent state (puterReady, auth).
     Prevents duplicate polling loops or multiple side-effects.
     Centralizes error handling for Puter.js load failures.

25.) In the pdf2img.ts file inside app/lib folder, below are the constituents of the async

     b.) lib is the pdf.js module object

     a.) pdf.js is loaded only when needed - Lazy loading

     c.) Multiple calls don’t trigger multiple imports - Concurrency safe
     d.) convertPdfToImage() doesn’t care how loading works - Clean API

27.) In the pdf2img.ts file inside app/lib folder, below are constituents of the function we
     export:
     a.) Promise resolution - 
        i.) resolve(value) fulfills a promise. This is resolve provided automatically by 
        new Promise.(alongside reject). Marks promise as fulfilled. Value passed to resolve
        becomes await result.
        ii.) await pauses until resolve is called
        iii.) Used here to wrap callback-based APIs
     b.) Blob is Raw binary data (image/pdf/etc.). It is a Result of canvas.toBlob. It is

        i.) Callback - the function in which we pass blob
        ii.) Type - Optional. The "image/png"

28.) In the pdf2img.ts file inside app/lib folder, the below line has a deep concept called
     web worker working in it:
     lib.GlobalWorkerOptions.workerSrc = "/pdf.worker.min.mjs";
     This line tells pdf.js: “This is the file you should use to run PDF processing in a Web
     Worker.”
     A Web Worker is a separate background thread that runs heavy work off the main UI thread.
     It prevents UI freezing. PDF parsing is CPU-heavy. It involves parsing text, fonts, 
     images. It is very slow on the main thread so pdf.js uses a worker by default.
     pdf.js has two parts:
        i.) Main library (you import this) - pdfjs-dist/build/pdf.mjs
        This manages API, coordinates rendering, talks to the worker.
        ii.) Worker file (runs in background) - pdf.worker.min.mjs
        This parses PDF bytes, extracts page data, sends results back to main thread.
    We need to set workerSrc manually because pdf.js does not know where worker file is
    as there are many bundlers (Vite, Webpack, Remix), different folder structures, different
    hosting setups. 
    Worker file must be publicly accessible. Without it, pdf.js fails or slows down.
    GlobalWorkerOptions is there because pdf.js expects one worker configuration that is 
    shared across all documents, set once and reused everywhere. That’s why it’s set during
    library load.
